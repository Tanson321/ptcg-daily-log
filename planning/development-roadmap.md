# PTCG Daily Log 開発ロードマップ

作成日: 2026-05-31

## 基本方針

このプロジェクトは「毎日の思考ログを、あとから読める考察記事へ変換する編集基盤」として育てる。短期では生成と編集の安定性を上げ、中期では記事資産を探しやすくし、長期ではカード・デッキ・対面・環境メタの研究ログとして機能させる。

## Phase 0: 安定化

目安: 1週間

### 目的

既存機能を壊さず、日常運用で詰まる箇所を潰す。

### やること

- READMEを実運用向けに書き換える。
- GitHub Actions入力とCMS入力の整合性を本番で確認する。
- `today`, `date`, `week`, `period` の実行例を運用メモに残す。
- 生成ページのエラー表示を `alert` から画面内のステータス表示に置き換える。
- GitHub Actions dispatch失敗時のエラーメッセージをCMSに返す。
- `scripts/fetch-today.js` と `scripts/generate-post.js` の日付範囲計算をテストできるように関数分離する。

### 完了条件

- 本番CMSから4種類の生成を起動できる。
- 失敗時に「何が原因か」がCMS画面上で分かる。
- 日付範囲の回帰テストが最低限ある。

## Phase 1: 生成品質と再現性

目安: 2週間

### 目的

生成される記事がログ範囲から逸脱しにくく、編集開始地点として安定する状態を作る。

### やること

- Gemini出力のfrontmatter検証を追加する。
- frontmatter欠落・壊れたYAMLの自動リトライまたは修復を入れる。
- Discordログに「取得範囲」「対象チャンネル」「メッセージ件数」をmetadataとして残す。
- プロンプトに「期間外の推測を避ける」制約を追加する。
- 生成結果に `sourceLogPath` または `sourceRange` をfrontmatterとして残す。
- 同じ範囲で再生成した場合の上書き/別名保存ルールを決める。

### 完了条件

- 生成記事から元ログ範囲を辿れる。
- 期間外の内容が混ざった場合に検知・修正しやすい。
- 同じ範囲を再生成しても運用が破綻しない。

## Phase 2: CMS編集体験

目安: 2〜3週間

### 目的

「AI下書きを確認して、少し直して、公開する」までを快適にする。

### やること

- Markdownプレビューを追加する。
- 保存前後の差分表示を追加する。
- draft statusを追加する。
  - `generated`
  - `editing`
  - `ready`
  - `published`
- 公開済み記事へのリンクをCMSに表示する。
- 画像アップロード後に即プレビューを表示する。
- tags入力をカンマ区切りからチップUIへ改善する。
- save/publish中の二重送信をより厳密に防ぐ。

### 完了条件

- CMSだけで編集判断が完結する。
- 公開前に記事の見え方を確認できる。
- 公開済み・未公開の状態が一覧で分かる。

## Phase 3: 公開サイト強化

目安: 2〜4週間

### 目的

蓄積した記事を「後から探せる研究ログ」にする。

### やること

- 記事タイプ別フィルタを追加する。
- タグページを独立させる。
- 月別アーカイブページを独立させる。
- 関連記事表示を追加する。
- `searchText` の生成ルールを改善する。
- OGP/metadataを記事ごとに強化する。
- 記事内のカード名・デッキ名を将来の構造化に備えて抽出する。

### 完了条件

- タグ・月・記事タイプで自然に掘れる。
- 記事詳細から関連する過去ログへ戻れる。
- 公開サイトが単なる一覧ではなくアーカイブとして機能する。

## Phase 4: データモデル整理

目安: 1ヶ月

### 目的

運用が増えても破綻しない正本管理を決める。

### 選択肢

1. GitHub Markdownを正本にする
   - 長所: 差分管理が明確。移行しやすい。
   - 短所: CMS保存時の競合やAPI制限に弱い。
2. Vercel Blobを正本にする
   - 長所: 公開サイトと相性が良い。
   - 短所: 編集履歴や差分管理は別途必要。
3. DBを追加する
   - 長所: status、履歴、検索、構造化に強い。
   - 短所: 運用負荷が上がる。

### 推奨

短期はGitHub Markdownを正本に維持する。記事数と編集頻度が増え、statusや履歴管理が必要になった時点でDB導入を検討する。

## Phase 5: 研究ログ化

目安: 継続開発

### 目的

単なる記事アーカイブから、カード・デッキ・対面・仮説の研究データベースへ進化させる。

### やること

- カード名辞書を導入する。
- デッキタイプ・対面・検証テーマをfrontmatterへ構造化する。
- 記事から仮説・検証結果・未検証メモを抽出する。
- 「最近よく考えているテーマ」をダッシュボード化する。
- Discordログから未記事化トピックを抽出する。
- 大会・環境変化と考察ログを紐づける。

### 完了条件

- 過去の思考がテーマ別に再利用できる。
- 記事を書くためだけでなく、構築研究の補助線として使える。

## 優先順位

1. 本番生成の安定化
2. CMSのエラー可視化
3. Markdown/frontmatterの検証
4. READMEと運用手順整備
5. 編集プレビュー
6. 公開サイトの検索・分類強化

## 直近の推奨タスク

- `README.md` をルートに追加し、全体構成と運用手順を書く。
- `scripts/lib/date-range.js` のような小さな共通モジュールを作り、fetch/generateで重複している日付計算を統合する。
- Node標準の `node:test` で `today/date/week/period` の範囲テストを追加する。
- `/api/generate` のレスポンスエラーをUIに出す。
- 生成完了通知に対象rangeと日付を含める。
